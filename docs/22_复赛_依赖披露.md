## 一、总览

**商业 API 与闭源模型这一项必须分两层讲，混在一起讲就会说出可证伪的话。**

早先版本这里写的是「商业 API：完全未使用」。那句话在**运行时**成立，作为整体陈述
却是假的——公开的源码注释里记着某处 bootstrap 修复由 GPT Pro 指出，提交历史里
也写着「三份材料按 Gemini 3.7 Flash 评审意见修订」。2026-08-25 由外部审查
（GPT-5.6 Pro）指出，本节已按事实重写。

| 披露项 | 结论 |
|---|---|
| **运行时**商业 API / 闭源权重 | **无**。模型流水线里不含任何 API 调用、预训练大模型或第三方权重，全部推断在本机 CPU 完成 |
| **开发与审阅辅助**中的闭源模型 | **有，且用得很重**。详见第二节 |

| **最终提交模型用到的外部数据** | **没有**。见下方说明 |

### 最终提交的那条模型，一行外部数据都没用

这一点值得单独说，因为它与本文第四节列的两项外部公开资源看起来矛盾。

两项外部资源都用在**实验**里，不在**提交路径**上：化合物结构表用于整化合物留出的
结构表示实验，菌株基因组用于未见菌株的效应搬运实验。**两条路线都按预先写死的判据
做完并被否定**（增益落在打乱标签的带子里 / 未达预注册阈值），所以最终模型里
结构项权重为 0、菌株搬运不启用。

可以逐行核验：产出提交文件的 `scripts/models/predict_test.py` 只引入官方数据加载器、
训练边界守卫、设计矩阵与低秩分解四个模块，**不 import 任何与 SMILES、指纹、
基因组相关的东西**。

组委会 2026-08-12 的通知里写着「仅使用官方数据仍达到同等水平的方案，
我们将在方法创新性维度予以正面考量」。本方案恰好落在这一类里，但需要说明的是：
这不是一开始就打算只用官方数据，而是**两条外部资源路线都被自己的预注册判据否掉了**，
负结果连同判据、阳性对照与可验证性分析一并写在实验结果报告第五节。

### 3.2 直接依赖与它们各自被用在哪

版本锁在 `requirements.txt`；下表说明每个包**实际承担什么**，
以便评审判断哪些是数值关键路径、哪些只是外围。

| 包 | 版本 | 用途 | 是否影响数值结果 |
|---|---|---|---|

| pandas | 3.0.2 | 元数据读取与分组 | 是 |

| scikit-learn | 1.9.0 | **只用 `randomized_svd`**，即掩码 EM-PCA 里的截断 SVD | 是 |
| rdkit | 2024.9.5 | 只用于化合物结构表示（Morgan 指纹 + 8 个描述符） | 是（仅 LOCO 结构实验节） |
| matplotlib | 3.10.1 | 只用于出图 | **否** |

`requirements.txt` 里除直接依赖外，还固定了本机实际解析出的主要传递依赖
（joblib / threadpoolctl / pillow / python-dateutil / six / cycler / fonttools /
kiwisolver / packaging / pyparsing）。

⚠ 如实说明（R6-L2-05）：这**不是**严格意义上的完整 lock 文件——
仍有少量更深层的传递依赖由 pip 在安装时动态解析。若需要逐位一致的环境，
应在干净环境里生成真正的锁文件（`pip freeze` 全量或 `pip-compile`）。
本项目的数值结果只依赖上表六个包的行为，对更深层依赖的版本不敏感。

**为什么 scikit-learn 只用一个函数**：5,078 × 5,243 的完整 SVD 每次约 1 分钟，
乘上 EM 迭代与 K 网格要跑几小时；只取前 k 个奇异向量的随机化 SVD 快两个量级。
除此之外没有调用任何 sklearn 的模型、交叉验证或预处理组件——
划分、缺失掩码、正则选择全部自写，为的是让训练边界可被逐行核验。

复算入口：`python scripts/data/provenance.py`（打印环境快照与源码摘要）。

### 4.2 PubChem 公开转储 · 化合物名 → SMILES

| 项 | 值 |
|---|---|
| 文件 1 | `CID-Synonym-filtered.gz`　964,716,803 字节　SHA-256 `c6d57604dc0fe746a7f5672586b1828dc77d05591e142ce0d0a55c3348ad3a46` |
| 文件 2 | `CID-SMILES.gz`　1,483,381,486 字节　SHA-256 `b62cf763f38b0d4812340ed7285137ab305be0a7de1ccc16bd564e4429d176b0` |
| 来源 | https://ftp.ncbi.nlm.nih.gov/pubchem/Compound/Extras/ —— 与组委会推荐的「PubChem 检索 SMILES + RDKit 生成描述符」一致 |
| 取回日期 | 2026-08-05 |
| 解析脚本 | `scripts/data/resolve_smiles.py` |
| 产出 | `data/external/compound_smiles.csv`（54 个化合物） |
| 匹配质量 | 精确匹配 50 个；名称别名匹配 4 个（别名只断言名称，SMILES 仍由 PubChem 给出，`match_level` 列标注供复核） |

**这里有一个刻意的设计，值得单独说**：没有走 PubChem 的在线 API，而是下载全量公开
转储后在本机匹配。理由是合规——查 API 等于把赛事化合物名单逐条发给第三方服务器。
现在出去的只有对两个固定公开 URL 的 GET 请求，**化合物名单一个字都没离开本机**。
代价是 2.4 GB 下载与几分钟本地扫描，换来的是数据边界干净。

#### 一个必须披露的复现限制：这两个上游文件是滚动更新的

上表登记的 SHA-256 是我方 2026-08-05 取回时的值。2026-08-25 做干净环境复现测试时，
按同一地址重新下载，`CID-Synonym-filtered.gz` 的校验值对不上：

| | 大小 | SHA-256 前 16 位 |
|---|---|---|
| 我方 2026-08-05 取回 | 964,716,803 字节 | `c6d57604dc0fe746…` |
| 上游 2026-08-25 现值 | 968,456,680 字节 | `8f82d4ce02e4f1af…` |

服务器返回的 `Last-Modified` 是 `Tue, 25 Aug 2026 06:56:51 GMT`，即当天早上刚重新生成。
NCBI 的 `Compound/Extras/` 是**滚动目录**，不是带日期的归档快照，
**因此我方用过的那一版无法从该地址重新取回**。

我方脚本里的校验闸门在这一刻拒绝了继续，而不是拿一份不同的输入接着跑完
——这正是登记 SHA-256 的意义所在。若没有这道闸门，复现者会拿到一份
由更新后的同义词表生成的结构表，得出与本报告不同的数字，却以为复现成功了。

**修法**：把派生产物 `compound_smiles.csv`（54 行，8,200 字节，
SHA-256 `3863eed5d961856b5f0435e94382f760fd2eb7a24d0b3aa9429cf29a011e8ff9`）
**直接随提交物交付**并登记校验值，复现不再依赖一个会变的上游。
`scripts/setup_external.py` 保留了从 PubChem 重建的回退路径，
但会明确提示重建结果与本报告的数字不保证一致。

转储文件本身不入仓库（体积）。走回退路径时脚本不再对它们做 SHA 门槛校验
（拿旧值当门槛只会永远失败），改为如实记录本次实际取到的版本，
同时保留我方当初用的那个值以供对照。

## 六、测试集真值的使用边界

手册 2026-08 修订版第 15 页允许拿测试集真值自评，第 17 页禁止它进入训练或参与
任何统计量估计。这条边界在本方案里由代码结构强制，不靠自觉：

| 层 | 机制 |
|---|---|
| 常规入口 | `paths.assert_readable()` 见到测试蛋白文件一律抛异常；建模、评估台、出图、提交脚本全部只能走这条路 |

上面三项限制都可现场验证生效：把令牌写错、从 `scripts/eval_test/` 以外的地方调、
模型尚未冻结时调，逐一抛异常。

自评结果**只用于实验结果报告**，不参与任何模型选择或调参。

### 7.2 随机性从哪来，怎么固定

算法层涉及的随机源**全部显式固定**，逐个说明如下。
⚠ 边界要说清楚：这指的是我们代码里的随机环节。BLAS 的多线程归约次序、
Python 的哈希种子这类运行时因素不在此列，它们可能带来末位浮点差异，
所以逐位复现只在**同一环境内**成立。

| 随机环节 | 固定方式 | 位置 |
|---|---|---|
| 掩码 EM-PCA 的随机化 SVD | `seed=0` 硬编码传入 `randomized_svd(random_state=seed)` | `models/lowrank.py` `masked_pca` |
| LOCO 外层折的化合物分配 | `np.random.default_rng(20260805)` | `models/loco_response.py` |
| shuffled-label 对照 | `seed=1000+s`，s 为重复序号 | 同上 |
| 共享参照的同上下文置换 | `seed=20260805` | `scorer/authoritative_results.py` |
| 分组 bootstrap | `seed=20260805`；配对版 `seed=20260806` | `scorer/evaluate.py` |
| C-free 守卫的置换 | `np.random.default_rng(0)` | `models/baseline_cfree.py` |
| 菌株搬运的随机坐标零假设 | `seed=20260824` | `models/strain_transport.py` |
| 合规探针的破坏 | `seed=20260824` | `audit/train_boundary_probe.py` |

种子写死在代码里，不从命令行传，也不读环境变量——避免出现「换个种子结果就变」
却无从追溯的情况。

### 7.3 怎么确认拿到的源码就是产出这些数字的那一份

`results/AUTHORITATIVE.md` 的「代码与发布指纹」一节登记：

- `tree_digest`：`scripts/` 下全部 `.py` 按相对路径排序，逐个算 SHA-256，
  再把「路径 + 该文件摘要」依次拼接后整体做一次 SHA-256，取前 16 位。
  哈希前把 CRLF 归一成 LF，见 `data/provenance.py`
- 公开仓库的 tag 与 commit
- 运行环境版本

任何人 clone 对应 tag 后按同一规则重算，应得到同一个 `tree_digest`。
仓库根的 `.gitattributes` 强制全仓库 LF，保证 Windows 与 Linux 上算出同一个 `tree_digest`。
（它保的是**代码指纹**一致，不保证浮点运算结果逐位一致——那取决于 BLAS 后端。）

复算入口：`python scripts/data/provenance.py`。
